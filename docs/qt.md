# Qt 上位机开发方案

## 1. 文档目标

本文档用于规划 `DualArmRobot` 后续 Qt 上位机的整体开发方案，重点解决以下问题：

- 当前设备通信架构是否适合继续扩展
- 如何彻底避免多设备、多线程、多总线场景下的通信冲突
- Qt 应该如何接入，而不是只做一个“套在现有脚本外面的界面”
- 后续新增电机、夹爪、传感器、串口设备时，如何保持结构稳定

本文档的结论是：

`Qt 上位机必须建立在“统一通信调度层”之上，而不是让每个设备类各自打开串口、各自收发数据。`

这不是一次局部修补，而是一次面向后续扩展的重构。

---

## 2. 当前框架的问题

以 `ino_motor` 为例，当前代码已经具备单设备控制能力，但从系统设计角度看，存在以下隐患：

### 2.1 设备对象和通信对象耦合过深

当前 `InovanceServo` 继承自 `CanInterfaceUsb`，意味着：

- 电机对象本身就负责打开串口
- 电机对象本身就负责收发数据
- 电机对象本身就负责等待响应

这在单设备测试阶段是可行的，但在以下场景中会变得不稳定：

- 一个 CAN-USB 口挂多个节点
- 一个 Qt 程序同时管理多个设备
- 后台有实时轮询线程
- UI 上有频繁操作
- 后续接入其他总线协议

### 2.2 同一物理链路可能被多个对象争用

如果多个设备对象都直接打开同一个 `/dev/ttyUSB0`，会出现：

- 多对象同时写同一个串口
- 多对象同时读同一个串口
- 某个对象读取到本应属于另一个对象的响应
- 收发顺序不可控，调试困难

### 2.3 监控线程和控制线程会互相堵塞

当前碰撞保护、状态查询、实时显示等功能都会占用通信通道。如果后续继续增加：

- 扭矩轮询
- 位置轮询
- 电流轮询
- 报警轮询
- 其他设备轮询

那么控制命令就可能被监控任务阻塞，导致控制延迟上升。

### 2.4 Qt 主线程不能直接参与阻塞式通信

Qt GUI 主线程负责界面刷新。如果主线程直接做串口读写、阻塞等待响应，会导致：

- 界面卡死
- 按钮延迟
- 状态更新不及时
- 复杂场景下出现线程安全问题

因此，Qt 的接入不能只是“把终端程序换成按钮”，而是必须先重构通信架构。

## 3. 重构目标

本次 Qt 方案的核心目标如下：

### 3.1 功能目标

- 第一版支持同一条 USB-CAN 总线下多个电机节点统一管理
- 支持多节点同时在线监控，并可随时对单节点下发控制命令
- 支持多电机统一管理
- 支持后续接入其他设备
- 支持实时状态监控
- 支持错误提示、日志记录、报警联锁
- 支持分模块开发和逐步扩展

### 3.2 架构目标

- 一条物理总线只允许一个通信实体独占
- 所有通信统一进入调度层
- 业务逻辑不直接接触串口、CAN、TCP 等底层接口
- UI 只通过 signal/slot 与业务层交互
- 轮询、控制、急停等任务具有明确优先级

### 3.3 工程目标

- 易于调试
- 易于扩展
- 易于测试
- 易于记录日志和回放问题
- 后续支持更多协议时无需推翻整体结构

## 4. 总体架构

建议将系统拆分为四层：

### 4.1 Qt 界面层

职责：

- 展示设备状态
- 提供控制按钮、参数输入框、日志窗口
- 处理用户交互
- 不直接进行设备通信

示例对象：

- `MainWindow`
- `MotorPanel`
- `DevicePanel`
- `AlarmWidget`
- `LogWidget`

### 4.2 业务服务层

职责：

- 对外提供“设备能力”
- 不关心底层串口、CAN 报文细节
- 负责把 UI 意图转换成业务请求

这一层也可以明确叫做 `设备层`。

在 Qt 上位机里，更推荐这样理解：

- GUI 面向设备层
- 设备层面向通信层
- 通信层面向物理链路

这样做的好处是，按钮、页面、状态显示始终面对“设备能力”，而不是直接面对串口和报文。

示例对象：

- `MotorService`
- `GripperService`
- `SensorService`
- `SafetyService`

示例接口：

- `enableMotor(nodeId)`
- `disableMotor(nodeId)`
- `setMotorVelocity(nodeId, rpm)`
- `setMotorPosition(nodeId, degree)`
- `requestTorque(nodeId)`
- `startCommunication(deviceId)`
- `stopCommunication(deviceId)`
- `clearFault(deviceId)`
- `queryFault(deviceId)`

### 4.3 通信调度层

这是整个系统的核心。

职责：

- 统一接管所有物理通信
- 管理总线生命周期
- 管理请求队列
- 管理响应匹配
- 管理超时、重试、优先级
- 管理轮询任务

建议命名：

- `CommunicationManager`
- `BusManager`

它下面管理多个总线 worker：

- `CanBusWorker(/dev/ttyUSB0)`
- `CanBusWorker(/dev/ttyUSB1)`
- `SerialBusWorker(/dev/ttyACM0)`
- `TcpBusWorker(host, port)`

建议把“通信模块”再细分成几个稳定职责，而不是把所有事情塞进一个类：

- `BusWorker`
  负责打开、关闭、独占物理链路
- `FrameIO`
  负责原始数据发送和接收
- `FrameParser`
  负责切帧、校验、解包
- `BusConfig`
  负责波特率、超时、设备路径等参数
- `RequestScheduler`
  负责队列、优先级、超时和重试

这意味着你补充的第 1 点是成立的，但更优解不是单个“大通信类”，而是：

`通信层负责链路和调度，协议层负责报文语义，设备层负责设备能力。`

### 4.4 协议适配层

职责：

- 将业务请求编码为具体协议报文
- 将底层响应解码为业务结果
- 对协议细节进行隔离

示例对象：

- `CanopenMotorProtocol`
- `ModbusProtocol`
- `CustomSerialProtocol`

---

## 4.5 推荐职责映射

为了避免后期混层，建议从一开始就明确每层的边界。

### 4.5.1 通信层负责

- 打开和关闭通信口
- 设置通信参数，例如波特率、超时、校验参数
- 发送原始报文
- 接收原始报文
- 切帧、缓存、校验
- 请求排队
- 响应匹配
- 超时与重试

### 4.5.2 协议层负责

- 按协议构造请求报文
- 将响应报文解析为结构化结果
- 定义响应匹配规则
- 解释错误码、状态字、告警码

### 4.5.3 设备层负责

- 向 GUI 暴露设备操作接口
- 维护设备状态缓存
- 组织初始化流程
- 提供开始通信、结束通信、使能、失能、清故障、状态查询等设备能力
- 把协议结果转为 GUI 可直接使用的数据

### 4.5.4 GUI 层负责

- 采集用户输入
- 显示设备状态和日志
- 触发业务请求
- 不直接持有底层通信对象

## 5. 解决通信冲突的核心方案

本项目后续的所有通信实现都应遵守以下规则。

### 5.1 一条物理总线，一个唯一 worker

这是第一原则。

例如：

- `/dev/ttyUSB0` 只能由一个 `CanBusWorker` 打开
- `/dev/ttyUSB1` 只能由一个 `CanBusWorker` 打开
- 某个 TCP 连接只能由一个 `TcpBusWorker` 管理

不允许多个设备对象分别打开同一个物理接口。

这条规则解决的是最严重的冲突来源：`多个对象竞争同一物理通信资源`。

### 5.2 所有请求统一进入队列

同一总线上的所有请求必须统一排队处理，不能由各模块自行发送。

请求来源可能包括：

- UI 手动控制
- 后台监控轮询
- 初始化流程
- 故障恢复流程
- 安全联锁触发

所有这些请求最终都应进入 `BusWorker` 的统一队列。

### 5.3 同一总线默认串行请求-响应

对电机控制、串口设备等典型请求-响应场景，推荐默认采用串行模式：

- 同一时刻只发送一个“需要等待响应”的请求
- 等待该请求完成或超时
- 再处理下一个请求

优点：

- 响应匹配逻辑简单
- 超时逻辑简单
- 排错容易
- 最适合早期稳定落地

在后期确有必要时，再对特定协议局部优化，而不是一开始就做复杂并发。

### 5.4 每个请求必须有明确的事务描述

建议定义统一的通信请求结构，例如：

- `requestId`
- `busId`
- `protocolType`
- `deviceId`
- `commandType`
- `payload`
- `timeoutMs`
- `priority`
- `expectedResponseMatcher`

这样做的目的不是为了“形式完整”，而是为了后期能够：

- 准确匹配响应
- 记录日志
- 跟踪错误
- 统计延迟
- 排查总线拥塞

### 5.5 响应匹配由通信层统一负责

不能由 UI 或设备业务层直接在外部等待底层响应。

响应匹配应由 `BusWorker` 负责，匹配条件因协议而异：

- CANopen：`can_id + index + subindex + 命令字`
- 串口协议：`帧头 + 设备地址 + 功能码 + 序号`
- TCP 协议：`请求序号 + 消息类型`

业务层只收到“成功/失败/数据结果”，不应自己处理底层帧匹配。

### 5.6 轮询任务必须由调度层统一管理

不允许每个模块自己起一个线程死循环轮询设备。

对于本项目第一版 Qt 上位机，这一条不是可选优化，而是首版必须能力。因为首版就要求：

- 同一总线多节点同时在线监控
- UI 可随时对单个节点发起控制命令
- 轮询监控不能阻塞控制主流程

正确方式是：

- 业务层向 `CommunicationManager` 注册一个轮询任务
- 调度层按周期安排这些任务
- 在总线繁忙时自动限流、降频、跳过低优先级刷新

示例：

- 扭矩监控：100 ms
- 位置监控：50 ms
- 温度监控：500 ms
- 设备在线状态：1000 ms

这样可以避免多个线程直接争用同一物理链路。

### 5.7 引入优先级机制

建议请求至少分为三类：

- `Critical`
- `Control`
- `Monitoring`

含义如下：

- `Critical`：急停、失能、故障复位、安全联锁动作
- `Control`：使能、速度设定、位置设定、模式切换
- `Monitoring`：扭矩读取、状态查询、温度查询、周期刷新

调度原则：

- `Critical` 可抢占或插队
- `Control` 优先于 `Monitoring`
- `Monitoring` 可以丢帧、跳过、合并

结合当前项目已确认需求，第一版至少应明确以下优先级：

- `Critical`：急停、失能、故障复位
- `Control`：使能、速度设定、位置设定、模式切换
- `Monitoring`：位置、速度、转矩、电流、在线状态、故障状态等周期刷新

这条规则对于 Qt 上位机非常重要，因为界面数据显示允许偶尔不刷新，但急停绝不能等待太久。

### 5.8 UI 主线程禁止直接访问物理设备

Qt 主线程只允许：

- 发起业务请求
- 接收业务结果
- 更新界面

不允许：

- 直接调用阻塞式串口读写
- 直接等待设备响应
- 直接操作总线对象

这条规则保证界面始终流畅，并降低线程安全风险。

## 6. Qt 落地方式

### 6.0 一个总线一个 worker 的定义

“一个总线一个 worker” 的含义是：

`一条实际存在的物理通信链路，只允许一个后台执行单元独占管理。`

例如：

- `/dev/ttyUSB0` 是一条实际的 USB-CAN 链路
- 即使它下面挂了多个电机节点，例如 `0x601`、`0x602`
- 它们仍然属于同一条总线
- 因此只能有一个 `CanBusWorker(/dev/ttyUSB0)` 打开并管理这条链路

不允许出现以下情况：

- 电机 A 自己打开 `/dev/ttyUSB0`
- 电机 B 也自己打开 `/dev/ttyUSB0`

因为这样会导致：

- 多个对象同时向同一链路发送数据
- 多个对象同时抢占接收数据
- 响应报文被错误对象读走
- 总线状态难以追踪和调试

因此，正确的结构应该是：

- `CanBusWorker(/dev/ttyUSB0)` 独占总线
- 多个设备服务，例如 `MotorService(0x601)`、`MotorService(0x602)`，都通过它提交请求
- worker 统一负责发送、接收、排队、匹配响应、回传结果

### 6.1 Qt 中的线程模型

建议采用：

- `QObject + QThread` 的 worker 模式

推荐组织方式：

- `CommunicationManager` 存在于主线程或业务控制层
- 每个 `BusWorker` 是一个 `QObject`
- 每个 `BusWorker` 移动到自己的 `QThread`
- 该线程独占对应物理链路

示意：

```text
MainWindow
  -> MotorService
  -> CommunicationManager
       -> CanBusWorker(/dev/ttyUSB0) in QThread A
       -> CanBusWorker(/dev/ttyUSB1) in QThread B
       -> SerialBusWorker(/dev/ttyACM0) in QThread C
```

### 6.1.1 本项目是否需要多线程

需要，而且这是推荐方案。

建议的线程划分如下：

- `主线程`
  负责 Qt GUI、页面刷新、用户交互
- `通信线程`
  每条总线一个 worker 所在的专属线程
- `可选后台线程`
  用于日志写盘、录包、文件导出等非实时任务

原因如下：

- GUI 主线程不能被阻塞式 IO 占住
- 不同总线之间应互不影响
- 通信收发和界面刷新应解耦
- worker 在线程内串行处理本总线请求，最容易保证稳定性

因此，本项目应当明确采用 `多线程` 架构。

### 6.1.2 本项目是否需要多进程

当前阶段不建议。

多进程当然可以实现，例如：

- GUI 一个进程
- 通信服务一个进程
- 日志服务一个进程

但对于当前项目阶段，多进程会显著增加复杂度：

- 需要额外的进程间通信机制
- 启动、退出、异常恢复更复杂
- 调试成本更高
- 部署和运行管理更重

在当前目标下，更合理的选择是：

- `单进程`
- `多线程`
- `每条总线一个 worker`
- `通过 signal/slot 在线程间传递请求和结果`

只有当后期出现以下明确需求时，才考虑多进程：

- 需要把通信服务独立部署
- 需要跨程序共享设备访问
- 需要更强的进程隔离能力
- 单进程稳定性无法满足要求

因此，当前建议的正式结论是：

`Qt 上位机采用单进程、多线程架构；不在第一阶段引入多进程。`

### 6.2 Qt 中 signal/slot 的角色

signal/slot 在本项目中主要用于层间解耦，而不是直接代替协议逻辑。

推荐的数据流：

```text
用户点击按钮
-> UI 发出 signal
-> MotorService 接收并封装业务请求
-> CommunicationManager 分发到对应 BusWorker
-> BusWorker 在线程中执行收发
-> BusWorker 发出完成 signal
-> MotorService 转换为业务结果
-> UI 更新显示
```

状态上报也走类似路径：

```text
BusWorker 收到设备状态
-> 协议层解析
-> MotorService 更新缓存
-> 发出 torqueUpdated / stateChanged / faultOccurred
-> UI 刷新
```

### 6.2.1 signal/slot 具体参与的位置

你补充的第 3 点是正确的，但建议把它的职责限定清楚：

- signal/slot 负责跨线程和跨模块传递事件
- signal/slot 不负责协议解析
- signal/slot 不替代请求队列和响应匹配

推荐用法如下：

- UI 发 signal 给设备层
  例如：开始通信、停止通信、使能、设置速度、清故障
- 设备层发 signal 给通信层
  例如：提交通信请求、启动轮询、停止轮询
- 通信层发 signal 给设备层
  例如：请求完成、请求失败、设备离线、收到状态更新
- 设备层发 signal 给 UI
  例如：连接状态变化、故障反馈、日志更新、实时状态变化

因此，signal/slot 是整个 Qt 架构的连接方式，不是通信协议本身。

### 6.2.2 典型设备操作链路

以“开始通信”和“故障反馈”为例：

```text
用户点击“开始通信”
-> MotorPanel 发出 startRequested(nodeId)
-> MotorService::startCommunication(nodeId)
-> CommunicationManager 提交初始化请求
-> CanBusWorker 打开总线并发送初始化报文
-> 协议层解析返回状态
-> MotorService 更新 online/enabled/fault 状态
-> MotorService 发出 communicationStarted / stateChanged
-> UI 更新连接状态
```

```text
设备返回故障状态
-> CanBusWorker 收到原始帧
-> Protocol 解析为 fault event
-> MotorService 更新 faultCode / faultText
-> MotorService 发出 faultOccurred(nodeId, faultInfo)
-> UI 弹出报警或点亮状态灯
```

### 6.3 Qt 中的模块建议

建议 Qt 工程模块化组织如下：

```text
qt_app/
├── ui/                  # 界面层
├── services/            # 业务服务层
├── communication/       # 通信调度层
├── protocols/           # 协议适配层
├── models/              # 状态模型、数据结构
├── logging/             # 日志与录包
└── safety/              # 安全联锁与告警
```

- `collisionTriggered`
- `lastUpdateTime`

第一版建议分两层定义：

- 首版必须项：`online`、`enabled`、`faultCode`、`faultText`、`mode`、`position`、`velocity`、`torque`、`current`、`collisionTriggered`
- 首版可选项：`temperature`、`positionDeviation`

业务层和 UI 层应尽量读取状态缓存，而不是每次都即时访问设备。

## 8. 开发流程建议

建议按照以下阶段推进，而不是一次性把所有内容写完。

### 阶段 1：通信核心层重构

目标：

- 脱离当前“设备类直接持有串口”的模式
- 建立统一通信调度层
- 支撑同一总线下多个电机节点共享一个 worker

本阶段交付：

- `CommunicationManager`
- `AbstractBusWorker`
- `CanBusWorker`
- 请求队列
- 响应匹配器
- 超时与日志基础设施

验收标准：

- 同一总线只存在一个 worker
- 多个请求可以稳定排队执行
- 可以记录每条请求和响应
- 同一总线多节点请求与监控可共存，且不会互相抢占底层物理接口

### 阶段 2：协议适配层拆分

目标：

- 把 CANopen、电机协议、其他串口协议从业务层抽出来

本阶段交付：

- `CanopenMotorProtocol`
- 通用请求编码器/响应解析器
- 错误码解析

验收标准：

- 协议细节不再散落在 UI 或业务逻辑里
- 新设备协议可以独立接入

### 阶段 3：电机业务服务层重构

目标：

- 在新通信层之上重建电机控制能力

本阶段交付：

- `MotorService`
- `MotorStateModel`
- 初始化流程
- 使能/失能/急停/速度/位置等标准接口
- 状态订阅机制
- 单节点操作接口
- 批量安全操作接口（批量使能、批量失能、批量故障复位、批量急停）

验收标准：

- 业务层不再直接读写物理接口
- 单电机与多电机都可统一操作
- 单节点控制和批量安全操作都通过统一 service 入口完成

### 阶段 4：Qt UI 最小闭环

目标：

- 实现可用的最小上位机

建议先做的页面：

- 设备连接页
- 电机控制页
- 实时状态页
- 日志页

最小功能集：

- 选择总线
- 连接/断开
- 手动配置节点列表
- 自动扫描在线节点
- 选择电机节点
- 使能/失能/急停
- 批量使能/批量失能/批量故障复位/批量急停
- 设置速度/位置
- 实时显示在线状态、故障状态、位置、速度、扭矩、电流、碰撞触发状态
- 故障弹窗或明显状态提示
- 界面日志显示

验收标准：

- UI 不阻塞
- 单总线多节点稳定
- 基础控制逻辑完整

### 阶段 5：安全与调度增强

目标：

- 在稳定控制基础上增加保护能力

本阶段交付：

- 轮询任务统一调度
- 优先级队列
- 碰撞保护接入
- 故障弹窗和状态灯
- 通信异常恢复机制

验收标准：

- 监控不会干扰控制主流程
- 紧急命令响应优先
- 异常场景可观察、可恢复

说明：

- 第一版 Qt 中碰撞保护只要求展示触发状态，不要求在 UI 开放参数配置
- 自动联锁策略可在后续阶段细化，首版先不把恢复策略写死

### 阶段 6：多设备扩展

目标：

- 支持更多设备类型

本阶段交付：

- 新设备 service
- 新设备 protocol adapter
- 多总线管理
- 多设备统一监控

验收标准：

- 新设备接入不破坏旧架构
- 不因设备增加而重新设计通信核心

## 9. 风险与规避策略

### 9.1 风险：一开始就照旧接口硬接 Qt

问题：

- 表面开发速度快
- 实际会把历史耦合带进 GUI
- 后续很快失控

规避：

- 先做通信核心层抽象
- 再接业务层
- 最后接 UI

### 9.2 风险：过早追求高并发

问题：

- 请求和响应关联复杂
- 超时、重试、异常恢复难度大

规避：

- 先做串行请求-响应模型
- 稳定后再局部优化

### 9.3 风险：各模块自行起轮询线程

问题：

- 总线拥塞
- 响应错配
- 逻辑难排查

规避：

- 所有轮询统一进入调度层

### 9.4 风险：UI 直接使用底层设备对象

问题：

- 界面线程被阻塞
- 线程安全隐患高

规避：

- UI 只通过 service 访问能力
- UI 绝不直接操作总线 worker

## 10. 推荐的初始实现边界

为了尽快形成稳定闭环，第一版 Qt 上位机建议只覆盖以下范围：

- 只支持一个通信协议族：CANopen 电机
- 只支持一个设备域：电机
- 只做一个总线 worker 类型：`CanBusWorker`
- 只实现最小必要页面
- 只实现最关键命令和状态显示
- 首版即支持同一条总线下多个电机节点
- 节点接入方式为“手动配置为主，自动扫描为辅”
- 只实现界面日志，不在第一版引入文件日志和原始报文录包

第一版不急着做：

- 全部设备统一接入
- 复杂权限系统
- 复杂脚本编排
- 过早的数据持久化
- 复杂插件机制

先把“稳定通信 + 清晰分层 + Qt 闭环”做出来，后面扩展会轻松很多。

## 11. 当前建议结论

本项目后续 Qt 上位机的建设，不应基于现有“设备类直接通信”的模式继续叠加功能，而应采用以下路线：

1. 先重构通信层，建立统一调度机制
2. 再拆出协议层和业务服务层
3. 最后让 Qt 通过 signal/slot 接入这些稳定接口

关于通信冲突的最终方案，结论如下：

- 一条物理总线只能有一个 worker 独占
- 所有通信必须统一进入调度层
- 同一总线默认串行处理请求-响应
- 轮询任务统一调度，不允许模块私自开 IO 线程
- UI 主线程绝不直接访问物理设备
- 通过优先级机制保证急停、安全命令优先执行

针对当前第一版范围，还应明确：

- 第一版验收对象不是“单总线单电机演示”，而是“单总线多节点可稳定运行的上位机闭环”
- 首版必须同时满足单节点控制、批量安全操作、实时状态监控三类场景
- 节点管理采用手动配置为主、自动扫描辅助的方式
- 故障处理做到增强型：状态提示明显、支持手动复位、写入界面日志

如果后续按本方案推进，那么：

- 当前电机控制能平滑迁移
- 后续新增设备不会推翻整体架构
- Qt 可以真正成为稳定的上位机，而不是界面化脚本
